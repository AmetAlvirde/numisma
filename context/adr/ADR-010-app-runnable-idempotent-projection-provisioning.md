# App-runnable idempotent projection provisioning (grants through the pg driver)

_Made during: MVI — web-app tracer prototype→reliable conversion (PRD #121), provisioning slice #123. This is the PRD's P3 open question ("grant-provisioning mechanism earns an ADR only if the choice is a genuine trade-off"), resolved here._
_Scope: product_
_Status: accepted_

The tracer prototype provisioned the ADR-007 projection out-of-band with a hand-run, undocumented `psql "$SUPERUSER_URL" -f schema.sql -v writer_role=... -v reader_role=...`, and `schema.sql` was a single file split at a literal `-- >>> GRANTS` marker so the push shell's node-postgres `--init` could run the DDL half while skipping the psql-meta-command grants half. This ADR replaces that with **app-runnable, idempotent, driver-only provisioning**: `pnpm db:provision` applies the DDL (`schema.sql`, `CREATE TABLE IF NOT EXISTS`) and then the ADR-007 two-role grants — generated **in code** from validated role names by `buildGrantStatements()` and sent straight to the pg driver — using a **one-shot admin credential** (`PROJECTION_ADMIN_DATABASE_URL`). Grants (`GRANT`/`REVOKE`) and the DDL are all idempotent, so re-running is a no-op; DDL and grants now live in **physically separate producers** (`schema.sql` is DDL-only; grants come only from `provision.ts`), so the marker-split coupling is gone. The choice is a genuine trade-off — it introduces a third, provisioning-time credential regime and moves the grant contract out of psql — so it earns this ADR rather than an ADR-007 implementation note.

## Considered Options

- **App-runnable idempotent GRANT/REVOKE through the node-postgres driver (CHOSEN).** One command (`pnpm db:provision`), no `psql`, no meta-commands, reproducible in CI and on a laptop. Role names are validated against `^[a-z_][a-z0-9_]*$` before interpolation, so a stray `:`, `"`, or `;` can never reach the driver. The cost paid deliberately: provisioning grants needs a credential that can `GRANT`, which neither the SELECT-only reader nor the no-DELETE writer holds, so a **one-shot admin/owner credential** is introduced — used only at provisioning time, held by no running service.
- **A migration tool (e.g. node-pg-migrate / Drizzle / Flyway) — REJECTED for this increment.** It would give ordered, versioned migrations, but the projection is a **disposable, re-projectable view** (ADR-007 §8.2), not a store whose history must be migrated: a read-model schema change is a **re-push, never a migration** (ADR-007). A migration-history tool would add a dependency, a `_migrations` bookkeeping table, and a mental model (forward-only history) that actively contradicts the "nuke-and-re-project" property. Idempotent re-runnable provisioning is the honest shape for a disposable view.
- **Vendored SQL + a documented psql runbook — REJECTED as the primary mechanism.** Keeping the psql path (even documented) leaves the psql meta-command coupling and a hand-run step: it cannot be exercised by the node-postgres test substrate, and the `-- >>> GRANTS` split remains a live footgun (a reworded comment silently skips grants, or feeds `:"writer_role"` to the driver). The auth store's schema, by contrast, **is** vendored SQL — see below — because it is not a re-projectable view; the projection grants are code because they must be asserted by a driver-run test.

## Consequences

- **A three-credential topology, with the admin cred fenced to provisioning time.** Runtime is unchanged and still split: reader = SELECT-only (`PROJECTION_DATABASE_URL`), writer = no-DELETE (`PROJECTION_WRITE_DATABASE_URL`). Provisioning adds `PROJECTION_ADMIN_DATABASE_URL` (superuser / table owner), used only by `pnpm db:provision` and held by no running service. ADR-007's structural one-way / split-cred runtime guarantee is preserved intact — the admin cred is not a runtime surface.
- **The marker-slice coupling is eliminated structurally.** `schema.sql` is DDL-only (no `GRANT`, no `REVOKE`, no `:"var"`); grants are produced only by `buildGrantStatements()`. A reworded comment can neither silently skip the grants nor pass a psql meta-command to the driver — and `provision.test.ts` asserts the executable DDL stays grant-free and meta-command-free.
- **The ADR-007 credential invariants become a CI-assertable fact.** The manual 8/8 probe is now `provision.integration.test.ts`, run against a **real throwaway Postgres** (pg-mem cannot enforce role privileges) via the shared `pg-substrate.testkit.ts` substrate. It is gated on `NUMISMA_TEST_DATABASE_URL` and skips loudly when absent, so `pnpm test` still passes without Postgres. The substrate is deliberately singular and reusable — slice #127 (push upsert idempotency) reuses `createThrowawayDb()` + `provisionProjection()`.
- **Login roles are a setup precondition, not provisioning's job.** `db:provision` grants privileges to `PROJECTION_WRITER_ROLE` / `PROJECTION_READER_ROLE` (defaults `numisma_push` / `numisma_web`); the roles must already exist. Documented in `docs/projection-provisioning.md`.
- **The auth store is provisioned by a parallel-but-different deterministic path.** The Better Auth `numisma_auth` schema (ADR-008) is **vendored** SQL generated by the **pinned** `@better-auth/cli@1.4.21` (the CLI versions independently of `better-auth@1.6.23`; there is no `1.6.23` CLI, so `@latest` is replaced by a pin) and applied idempotently by `pnpm auth:apply`. Vendoring (not code-generated grants) is right there because the auth DB is genuine, non-re-derivable state, not a re-projectable view.

### The three SDP tests

- **Hard to reverse.** Once the cloud projection is provisioned this way and CI asserts the grant invariants against it, the provisioning contract (which credential does what, where grants come from, what the test substrate expects) is load-bearing across local and Neon. Reverting to the psql-marker split would re-open the coupling the test now guards and break the shared substrate slice #127 builds on.
- **Surprising without context.** ADR-007 says the web holds a read-only cred and the push job holds the sole write cred — a reader would not expect a **third** admin credential to appear at provisioning time, nor that the grants moved out of `schema.sql` into application code. Both are deliberate: the admin cred is the minimum privilege that can `GRANT`, and code-generated grants are what make the invariant driver-testable.
- **A real trade-off.** App-runnable idempotent grants (reproducible, driver-testable, CI-assertable — but a new one-shot admin credential and grants-as-code) were chosen over a migration tool (versioned history — but contradicts the disposable-view model and adds a dependency) and over vendored-SQL-plus-psql-runbook (keeps the meta-command coupling and a hand-run step, untestable by the node substrate). The admin credential was accepted deliberately, bought back by fencing it to provisioning time so the runtime split-cred guarantee is untouched.

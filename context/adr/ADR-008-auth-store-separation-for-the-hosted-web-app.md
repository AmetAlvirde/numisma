# Auth-store separation for the hosted web app

_Made during: MVI — web-app tracer prototype→reliable conversion (branch `feature/web-app-tracer`, commit a41e486); ratified at PRD synthesis 2026-07-07, backed by two-phase prototype evidence (local + live Vercel/Neon, phone-verified)._
_Scope: product_
_Status: accepted_

ADR-007 §Consequences states that "the web app holds a **read-only** DB credential." The tracer prototype revealed that this is literally true only of the *projection* store. The live web access surface in fact holds **two** credentials against **two physically separate** databases: a **read-write** credential on a `numisma_auth` database that self-hosted Better Auth owns (tables: `user`, `session`, `account`, `verification`), and the ADR-007 **read-only** credential on the `numisma_projection` database (table: `composition_snapshot`). This ADR **refines ADR-007** by making that two-credential posture explicit and load-bearing. The web surface runs **self-hosted auth (Better Auth, email+password)** against its **own** auth DB, holding an RW credential **scoped to that auth DB only**; ADR-007's projection split is left exactly as-is (read-only web cred vs. sole-write push cred). Auth store and projection store are **provably disjoint** — different databases, different credentials — such that the auth code path never touches the `PROJECTION_*` credentials and the RW auth credential cannot reach the projection table. The prototype proved this on both local Postgres and live Neon: `numisma_auth` = {`user`, `session`, `account`, `verification`}, `numisma_projection` = {`composition_snapshot`} only, verified disjoint.

## Considered Options

- **Self-hosted Better Auth on its own DB (CHOSEN).** On-ethos for a local-first, self-owned system: no third-party identity regime, free, and native to the chosen framework, keeping all auth state under the app's own control. The cost paid deliberately is that the web app now holds a *write* credential — but that credential is structurally fenced onto a **separate** database and cannot reach the projection. This is what keeps ADR-007's one-way guarantee (nothing but the push job writes the projection) literally, not merely conventionally, true.
- **A third-party hosted auth regime (e.g. an external identity provider) — REJECTED.** It would remove the self-held write credential, but at the price of a new external vendor and secret regime — a fresh "hosted surface" tripwire and an outside party in the identity path. Off-ethos for a system whose whole posture (ADR-006, ADR-007) is self-owned and local-first.
- **Putting auth tables inside the projection DB — REJECTED as an ADR-007 violation.** Co-locating the auth tables in `numisma_projection` would force the web app to hold an **RW credential on the projection database**, destroying ADR-007's structural one-way guarantee: with a write cred on that DB, "nothing but the push job can write the projection" would collapse from a provable fact to a hope. Physical database separation is precisely the mechanism that keeps that guarantee true, so the auth store must live elsewhere.

## Consequences

- **The web app holds exactly two credentials.** RW on `numisma_auth`, RO on `numisma_projection`. The RW credential is scoped to the auth DB and **cannot mutate the projection**; the RO credential cannot write anything. ADR-007's split-credential enforcement is preserved intact on the projection side and extended, not weakened.
- **ADR-007's "web = read-only" now reads precisely.** Read-only **on the projection**; the auth DB is a separate store the web app **legitimately writes** — a single account's `user`/`session` rows. The earlier wording was a simplification that the live prototype forced into precision.
- **Disjointness is a compatibility invariant, not a nicety.** The reliable conversion must preserve it and (per the PRD) test it: `auth.ts` never references `PROJECTION_*`, and the two credentials never converge onto one database. This is the durable contract this ADR pins.
- **The auth DB is NOT a disposable, re-projectable view.** Unlike the projection DB under ADR-007 §8.2 (nuke-and-re-project yields an identical result), the auth DB holds genuine user/session state that is not re-derivable from the log. This is acceptable and bounded: it is single-account, tiny, and contains **no fund data** — only auth records. Its existence does not weaken ADR-007's "the DB is a disposable projection" property, which is a statement about the **projection** DB alone.
- **Adjacent, but out of scope: the deferred ADR-007 operational-security follow-on.** Encryption-at-rest, a secret manager, and rate-limit/lockout on the public auth endpoint remain deferred there and gate on real fund data. Disabling open self-service signup and seeding a single account is a *separate, in-cycle* auth-correctness concern, not this ADR's subject. But this ADR is what makes "single-tenant, single-account" coherent by **pinning where the account state lives** — in a fenced auth store, disjoint from the projection.

### The three SDP tests

- **Hard to reverse.** Once the app is live with a self-hosted auth regime and a two-credential posture, that shape is load-bearing — real sessions, a real account, and the RW/RO split baked into env and provisioning across local and Neon. It is not un-crossed by a code edit; sessions exist and the credential topology is deployed.
- **Surprising without context.** ADR-007 reads "the web app holds the read-only cred," so a reader would not expect the same web app to also hold a **write** credential on a **second** database. The separation is a deliberate structural choice made to keep ADR-007's guarantee literally true — not an oversight or an accidental privilege escalation.
- **A real trade-off.** Self-hosted Better Auth on its own DB (owned, free, on-ethos — but the app now holds a write cred that must be fenced away from the projection) was chosen over a third-party auth regime (no self-held write cred — but a new external vendor/secret regime, off-ethos for a self-owned, local-first system). The write credential was accepted deliberately, bought back by physical DB separation and the disjointness invariant.
